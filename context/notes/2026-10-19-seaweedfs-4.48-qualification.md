# SeaweedFS 4.48 isolated qualification

## Decision

Recommend a staged SeaweedFS 4.48 maintenance rollout with fresh, consistent
master/volume/filer backups and the existing stable DNS fix retained. The
isolated functional, restart, mixed-version, and rollback gates passed.
Production remains SeaweedFS 4.40, Seaweed CR generation 20, with ten of ten
pods ready at the read-only check. No production mutation, commit, push, or
deployment is part of this qualification.

Checks cover deterministic numbered objects, overwrites, deleted-object
absence, exact listing membership, HEAD lengths, range bytes, and a two-part
multipart object. Candidate writes and multipart completion are exercised
before rollback. Both HA gateways use distinct persistent LevelDB2 filers,
so a working gateway cannot hide a missing metadata replica. Eventual
metadata convergence is allowed within the bounded recovery gate.

The six-cycle restart dataset ended with 18 live objects, including six
objects acknowledged immediately before the restart sequence. Every final
body matched its deterministic bytes. Process kills preserve the host page
cache; this is not a power-loss durability proof. SIGTERM cases use a
20-second grace and may include forced shutdown after the grace. New harness
runs retain exit codes to distinguish these cases. The initial restart run
predates that exit-code instrumentation, so it must not be described as six
fully orderly shutdowns.

Additional 4.48 upstream regression executions passed:

- HTTP fresh-location, unchanged-location backoff, and partial replica failure:
  nine top-level executions.
- Filer whole-chunk recovery, partial failure, and cancellation: 18 executions.
- Master-client location, generation, invalidation, and lookup behavior:
  153 executions.
- Storage batch fsync failure, rollback, fail-closed handling, and corrupt index
  loading: 45 executions.

## What the address tests establish

The deterministic buffered-reader control shows the changed retry ordering.
4.40 exhausts approximately 13.19 seconds of configured backoff before
invalidating the location. 4.48 returns exact replacement bytes before the
first one-second backoff. Both versions already recover the single-location
streaming case promptly when the dead socket refuses connections.

In the distributed IP-move experiment, the baseline happened to receive the
new topology before its first read, while the candidate encountered a stale
connection. These are different observed states, so their timings cannot be
used as a release speedup comparison. The candidate's roughly 30-second
wait is consistent with its first TCP dial timeout: refreshing after failure
does not make a blackholed initial address fail immediately. Retain the
existing stable StatefulSet DNS advertisement and `ipBind: 0.0.0.0`.

Native GET/5xx metrics cannot detect every truncated HTTP 200 body. Keep the
full-body signed probes and log alerts. The 4.48 failure messages observed
in the lab retain patterns matched by the current read-failure alert, and
the actual signed probe succeeds against the candidate.

## Durability and rollout constraints

The configured memory index and LevelDB2 filer store remain readable across
the tested transition. The needle and superblock format definitions do not
change between the pinned versions. This is supporting evidence, not a
universal downgrade guarantee for every SeaweedFS feature. EC, tiering,
compaction, S3 versioning/object lock, filesystem mounts, and retired Iceberg
workloads are outside this qualification.

4.48 strengthens failed-fsync batch rollback and fail-closed behavior. It
does not automatically turn ordinary S3 writes into synchronous writes.
Filer storage rules still select fsync behavior, and LevelDB2 writes still
use default LevelDB write options. Longhorn block replicas cannot preserve
data that remains only in application or host buffers. No durability policy
was changed by this experiment.

If deployment is recommended after the final gates:

1. Use a maintenance window without Harbor retention, node maintenance, or
   other storage work. Capture current Longhorn, read-probe, storage/log-loss
   alert, and collector queue health. Verify queue capacity covers the
   expected interruption.
2. Quiesce writers and capture a consistent recoverable copy of all three
   master data sets, all three volume PVCs, and both filer metadata PVCs.
   Record the source revision, volume identity, image pins, and recovery
   procedure. A snapshot of only volume data does not preserve S3 metadata.
3. Retain the stable DNS/bind configuration. Pin the qualified image digest.
   Keep the operator version unchanged. Operator 1.0.39 uses independent
   RollingUpdate controllers for master, volume, and filer StatefulSets;
   changing the shared image does not itself enforce the component order
   used by this lab. Use the operator's component `version` fields to stage
   the rollout through Git instead of modifying its child workloads.
4. Advance masters with quorum checks, volumes one at a time, filers one at
   a time, then gateways. Single-copy Seaweed volumes can be unavailable
   while their owner restarts, even with healthy Longhorn replicas. Verify
   full bytes and both filer/gateway paths after each stage.
5. Stop on integrity errors, missing acknowledged data, persistent read
   failures, or storage degradation. The tested image rollback preserves
   candidate-written data, but a production format or integrity failure
   requires stopping writes and investigating on a clone. Never overwrite
   active PVCs with an older snapshot while new writes continue.
6. Afterward verify Flux revision, runtime digests, all pods, Longhorn,
   read-only gauges, both signed probes, Harbor cold pulls, Loki chunk
   reads and fresh log delivery, and alert routing. Observe at least the
   alert windows and the next Harbor retention run.

### Concrete image staging through operator 1.0.39

The qualified operator source is
`8ba00153c593258784e7cf7294e8ba6bdc1a055d`. `BaseMasterSpec`,
`BaseVolumeSpec`, `BaseFilerSpec`, and `BaseS3Spec` pass the component version
to `applyVersion`. The helper accepts a version containing `tag@digest` and
returns a digest-pinned OCI image reference. An actual helper test passed
with both qualified image pins; it is retained as `operator_image_test.go`.
The live served/storage v1 CRD also exposes all four component version fields
as strings without a tag-only pattern restriction. This was a read-only schema
check; no trial CR was submitted to production.

Keep the shared image at its existing baseline repository/tag reference while
staging. Verify that the running baseline resolves to the recorded 4.40 digest.
Set only the first component override:

```yaml
spec:
  image: chrislusf/seaweedfs:4.40
  master:
    version: 4.48@sha256:aba492e2a4e4c90bff795745e8e660affa1f09e7650f5981bd7bccd1a06cd931
```

This is a fragment for a future reviewed change, not a replacement CR.
The other components still inherit the unchanged 4.40 image. Wait for the
master StatefulSet and quorum acceptance before changing
`volume.version`, then `filer.version`, then `s3.version` in separate
reconciliations. Check each pod's actual digest, not only its tag.

After every group is accepted, normalize `spec.image` to the same candidate
digest and remove the component overrides only after confirming the rendered
pod templates remain identical. Do not pin the shared image early: the
operator deliberately ignores every component version override when
`spec.image` already contains a digest. For rollback, retain the tag-based
shared image and reverse each component pin to the baseline through the
same tested master/volume/filer/gateway order. If the shared pin has already
been normalized, reestablish equivalent candidate component pins before
staging the rollback. Live CRD validation and the operator's rendered objects
must still be checked before production approval.

## Failed attempts and limits

The first lab used an internal Docker network on which host port publication
was unavailable. It failed before workload startup and cleaned up. The first
HA bootstrap accepted bucket listing before writable topology existed; its
first object PUT returned 500. The harness now gates workload start on a real
write/read. The first source-test invocation ran in the old sparse source
checkout and failed on missing packages; the corrected runs used full pinned
source archives. An initial assertion expected the old streaming path to
fail, but it recovered. That assumption was removed; the corrected test
requires both streaming paths to work and separately measures the buffered
retry path. These failed fixtures remain in the raw evidence.

The final HA run completed at 22:49:10 UTC. It passed 25 explicit master
agreement checks and 48 full gateway verification phases. The final dataset
contained 34 live objects totaling 19,308,544 bytes in the main bucket,
plus the separately checked 262,144-byte object on the volume created by
4.48. Both gateways read those objects after all ten components returned
to 4.40. All three rolled-back volume servers reported `ReadOnly: false`
for every allocated volume; the stored needle version remained 3.

The six stable-DNS trials all passed and cleaned up. Once replacement topology
was registered, observed first-read times were 2.4–5.6 ms on 4.40 and
7.2–18.2 ms on 4.48. These single-machine emulated timings are functional
observations, not a production performance comparison. The deterministic
buffered-reader trials measured 13.1925–13.1944 seconds on 4.40 and
0.268–0.406 ms on 4.48. The old delay matches the explicit
1 + 1.5 + 2.25 + 3.375 + 5.0625-second backoff schedule; a refused local
socket removes the initial dial timeout from that specific comparison.

The final evidence-path guard was tested separately without Docker: rerunning
against an existing output directory exits with an error and preserves its
original bytes and file set. It was added after the final HA run started;
the successful experiment path and compatibility assertions were unchanged.

Final cleanup verification at 22:49:39 UTC found zero qualification containers
and zero qualification networks, including failed experiments. The final HA
run retained 40 termination records: every process exited with code 0 and none
was OOM-killed. Synthetic datasets, both offline baseline copies, logs, and
hash manifests remain in the ignored evidence directory. `final-summary.json`
records the assertions and harness-file hashes. No production resources or
secrets were used by the fault tests, and no temporary production resource
was created.

The tests do not reproduce Talos, Longhorn persistence, CoreDNS publication,
the Kubernetes operator, real Harbor/Loki load, or a host power failure.
They do not prove that every production object is intact. Full-stack restart
logs include transient missing topology and metadata-stream reconnect errors
while the isolated masters and volumes return; the asserted application
objects recover within the gate.

Build the Lever produced the retained harness and fixtures. Test Behavior,
Not Implementation selected full-byte and metadata checks after actual
component transitions. Explain the Number rejected the misleading IP-move
timing comparison and identified retry backoff versus initial dial timeout.
Prove It Works required candidate-written data to be read after rollback,
rather than accepting healthy processes as evidence of compatibility.

## Production-shaped follow-up

The rollout exposed that production masters use ephemeral `/tmp/m9333` Raft
state, while the first HA rehearsal retained master directories. The expanded
`--ephemeral-masters` rehearsal passed at 23:29:38 UTC and cleaned its Docker
resources at 23:29:49 UTC. It recreated all six master directories across
upgrade and rollback, passed 25 native Raft-health/quorum checks and 48 complete
gateway object checks, and finished with 34 objects. Candidate-written data,
including a candidate-created collection, remained readable after rollback.
See [rollout record](2026-10-19-seaweedfs-4.48-rollout.md) for the live readiness
finding, correction and recovery evidence. Private evidence is under
`.private/seaweedfs-4.48-qualification/ha-ephemeral-masters/`.
